# worker 并发解压不及 7z.exe 进程并行的原因分析

本文只解决一个问题：为什么 `sunpack_sevenzip_worker.exe` 单文件更快，但把并发
交给它一个进程不如启动 c 个 `7z.exe` 进程快，且 7z / XZ 差距最大。

所有结论都来自同一台机器、同一份 300 MiB 缓存语料上的对照实验，实验脚本与原始
JSON 一并列出，可复现。

## 1. 结论摘要

**公平计时后的最终结论**（第 3.10 节）：把"提取 + 强制刷盘"作为共同口径后，
**tar / tgz / zip 已经反超**（合计比 1.02 / 0.97 / 0.94），
**只剩 7z（1.16）与 xz（1.26）还有真实劣势**。

而这个劣势**既不是解码、也不是"等容量"**：

- **解码侧 worker 全面更快**（同口径对照：7z 0.95、xz 0.74、tar 0.23、tgz 0.39、
  zip 0.35、7z-split 0.82）。
- worker 的提取时间 795.9 ms 里已经包含"设备把整批 2400 MiB 全部写下"
  （2.94 GiB/s 的设备持续速率）；`7z.exe` 的 557 ms 只推了约 1.2 GiB，
  剩下约 1.2 GiB 留给刷盘段。
- 用 `max(解码, 设备写入)` 检验：7z 是 `max(507, ≈767) ≈ 767`，实测 796 ms，
  只多 29 ms——**解码与落盘几乎完全重叠**。
- 所有"加深队列"类改动（提交时归还、加深 writer 线程、放大缓冲池、放大每文件
  窗口）都被交替顺序的配对测量否掉了（第 3.5 / 3.8 / 3.9 节）。

几个被测量纠正的直觉：

- **8 个 IOCP 线程并没有"不持续提交"**。它们绝大部分时间阻塞在
  `GetQueuedCompletionStatus` 等**完成包**上（零 CPU，所以 CPU 指标看着很低），
  不是等在**工作包**上；线程加到 32 也不改变在飞深度。
- **"等写入容量"确实存在**：容量只在 IO 完成回调 `release_buffer()` 里归还，
  所以"未完成 IO 数"被窗口大小锁死（8 MiB 窗口 → `inflight_peak` 恰好 8）。
  但**把归还时机提前并不能提速**（第 3.8 节）。
- **`file_full` 计数不能当成吞吐瓶颈**。它是**每文件**上限的计数；每作业 2 个活跃
  文件 × 8 作业已经给出约 128 MiB 聚合在飞，超过设备饱和所需的约 88 MiB。
  放宽它四轮配对下来收益在 ±1.5% 内且符号不一致（第 3.9 节）。

按影响排序的根因：

| # | 根因 | 证据 |
| - | ---- | ---- |
| 1 | **计时口径**：`7z.exe` 返回时数据还在页缓存，worker 返回时已经落盘 | 7z 提取 557 ms + 刷盘 265 ms；worker 提取 796 ms + 刷盘 143 ms；"557 ms 内落盘 2400 MiB" = 4.4 GiB/s 超过设备能力（第 3.7 / 3.10 节） |
| 2 | **设备持续写入速率约 3.1–3.3 GiB/s 是硬下界**，7z 的提取段已贴着它 | 2400 MiB 在 3.0 GiB/s 下约 767 ms，worker 实测 796 ms（第 3.6 / 3.10 节） |
| 3 | 每作业解码并行度只有约 1 个核，c 增大后不再扩展（高并发天花板） | c=1 给满 32 额度也只有 1.2 核、解码器峰值额外额度恒为 1；c=8 8.2 核、c=16 仍 5.2–5.8 核，同期 7z.exe 从 8.8→13.1→20.6 核 |

**按卷共享 writer 这个设计本身是对的**（同一磁盘统一调度、统一异步 IO、空间 gate
只有一个权威），它的问题只是**流量控制口径**在设备饱和之前会先 binding：

- 生产侧容量 `file->inflight_bytes` / `job->inflight_bytes` 只在
  `release_buffer()`（IO 完成路径）里归还，于是"未完成 IO 数"成了"还能生产多少"
  的唯一来源，深度上限 = 窗口大小。这个耦合是真的，只是**提前归还换不来吞吐**
  （第 3.8 节配对：0.27% / −4.28%，符号都不一致）。
- 全卷共享一个 64 × 1 MiB 缓冲池；`buffers_empty` 计数里相当一部分是
  `producer_cv_.notify_all()` 造成的"醒了又睡"，不能直接当成饥饿次数。

不是根因的项（都被实测排除）：线程额度（`thread_capacity` 8/16/32/64）、每卷
writer 线程数（1/8/16/32）、缓冲区个数（64/256）、卷空间 gate、输入 prefetch。

## 2. 复现方法与新增诊断入口

复用 `worker-concurrency-300m` 的缓存语料与驱动，只替换被观测的变量。两个脚本都是
薄编排层，字节生成、解压、校验全部在原生侧完成：

```powershell
# 单变量消融（writer/额度/gate/buffer/prefetch），可选并发 7z.exe 参考
python benchmarks/scenarios/worker_concurrency_ablation.py `
  --worker native/sevenzip_bridge/build-probe/Release/sunpack_sevenzip_worker.exe `
  --format 7z --concurrency 4,8 --runs 2 --reference `
  --json-out benchmarks/results/_ablate_7z.json

# 输出路径相位消融（真实写入 / 内存接收器 / 无拷贝 / 预分配 / writer 宽度）
python benchmarks/scenarios/worker_writer_ablation.py `
  --worker native/sevenzip_bridge/build-probe/Release/sunpack_sevenzip_worker.exe `
  --format 7z --concurrency 1,4,8 --runs 2 `
  --json-out benchmarks/results/_writer_ablation_7z.json
```

探针二进制需要打开**已有的**编译开关，产品默认构建不含这些开关：

```powershell
cmake -S native/sevenzip_bridge -B native/sevenzip_bridge/build-probe `
  -G "Visual Studio 17 2022" -A x64 `
  -DSUP7Z_ENABLE_WRITER_PROBE=ON -DSUP7Z_ENABLE_PIPELINE_TIMING=ON
cmake --build native/sevenzip_bridge/build-probe --config Release `
  --target sunpack_sevenzip_worker --parallel
```

为回答"写入到底排了多深、一次写要多久"，扩展了已有的 `WriterProbe`（新增
`inflight` / `inflight_peak` / `queue_depth_peak` / `latency_ns` / `latency_count` /
`latency_peak_ns`），没有新增第二套诊断设施。该扩展只在
`SUP7Z_ENABLE_WRITER_PROBE=ON` 时编译，普通 worker 二进制不受影响。

测例固定为 `few_large:7z:non-solid`（2 × 150 MiB，LZMA2:25，`Blocks = 2`，
非 solid 每个成员一个 folder）。除第 3.4 节外都在 `--dry-run` / `7z t` 关闭输出
写入，那是**故意**的对照：它把"解码成本"和"写入成本"分开。

## 3. 测量结果

### 3.1 相位分解：时间花在等写入容量上，不是花在拷贝上

`few_large:7z:non-solid`，300 MiB × c 个作业，单位 ms，各行是相位累计时间
（跨作业、跨线程求和，不可当成墙钟相加）：

| 并发 | 模式 | 墙钟 | 核数 | producer | capacity_wait | copy | writefile | 排队 | 在飞峰值 | 单次写均值 |
| ---- | ---- | ---- | ---- | -------- | ------------- | ---- | --------- | ---- | -------- | ---------- |
| 1 | real | 200.0 | 0.86 | 63 | 39 | 21 | 106 | 3 | 1 | — |
| 1 | memory | 162.1 | 1.11 | 20 | 0 | 19 | 0 | 2 | 1 | 0.011 |
| 4 | real | 388.2 | 4.49 | 475 | 196 | 248 | 1056 | 1027 | 8 | 3.048 |
| 4 | memory | 280.7 | 4.14 | 114 | 0 | 105 | 0 | 12 | 1 | 0.011 |
| 8 | real | 833.3 | 5.94 | 2872 | 1956 | 791 | 1507 | 3835 | 8 | 9.593 |
| 8 | memory | 532.0 | 6.55 | 496 | 0 | 465 | 0 | 70 | 2 | 0.025 |
| 8 | memory-nocopy | 515.4 | 6.20 | 185 | 0 | 0 | 0 | 115 | — | — |

读法：

- producer 线程 2872 ms 里 1956 ms 停在 `capacity_wait`，真正做事的 `copy` 只有
  791 ms。也就是说，生产路径的成本主要是**等待**，不是拷贝。
- `copy` 不是根因：`memory-nocopy` 去掉了全部 791 ms 拷贝，只换来 532→515 ms
  （3%）的墙钟改善。
- 在飞写入深度在 c=4 和 c=8 都**恰好是 8**，而单次写要 3.0 / 9.6 ms。窗口 ×
  1/时延 = 833 MiB/s 的上限——正好等于观测到的吞吐。`7z.exe` 同期是 4.2 GiB/s。
- 磁盘不是瓶颈：整批 2400 MiB 实际落盘时延约 3.1–3.3 GiB/s，与 `7z.exe` 相同量级。
- `inflight_peak = 8` 不是巧合，它正好等于当时的每文件窗口（8 MiB / 1 MiB 缓冲）。
  第 3.5 节把窗口放开后它就跟着涨到 32，证明**深度上限 = 窗口大小**。

### 3.5 决定性实验：深度由窗口决定，不由 IOCP 线程数决定

把每文件窗口临时放到 32 MiB（`kDefaultFileInFlightBytes`），只改每卷 writer 线程数，
c=8、`few_large:7z:non-solid`，2 轮：

| writer 线程 | 墙钟 | 核数 | `inflight_peak` | 队列峰值 | 单次写均值 | `file_full` | `buffers_empty` |
| ----------- | ---- | ---- | --------------- | -------- | ---------- | ----------- | --------------- |
| 8 | 790.2 | 5.83 | 32 | 49 | 9.59 ms | 1 | 1415 |
| 16 | 766.1 | 6.33 | 27 | 33 | 10.03 ms | 8 | 1417 |
| 32 | 747.0 | 6.38 | 32 | 22 | 9.25 ms | 9 | 1504 |

结论：

- **线程数不是限流点**。8→32 线程只拿回约 5%，而在飞深度停在 27–32 不动，
  单次写时延也没有下降。多出来的线程只是在完成端口上更频繁地空转。
- 深度跟着**窗口**走：窗口 8 MiB → 在飞 8；窗口 32 MiB → 在飞 32。放窗口后
  `file_full` 从 1641 次掉到个位数。
- 32 MiB 在飞 ≈ 3.2 GiB/s，已经贴住设备持续速率；继续加深的边际收益接近零。
  这也解释了为什么 `buffers256`、`writers16/32` 都没有效果——它们都没动那个
  真正绑定深度的量。

### 3.6 设备侧的时延带宽积（判断窗口该多大的依据）

- 单作业、c=1：300 次写共 300 MiB，设备空闲，约 **0.2 ms/次**（约 5 GiB/s）。
- c=8、窗口 32 MiB：2400 次写，均值 **9.3–10.0 ms**，在飞 27–32 →
  Little 定律给出 **约 3.2 GiB/s** 的持续速率，与落盘计数器一致。
- 即：设备**持续**速率约 3.1–3.3 GiB/s，达到它需要约 **30 MiB 在飞**。
  默认的每文件 8 MiB 只有这个量的四分之一，所以生产侧必然被设备时延拖住。

### 3.7 计时口径：7z.exe 有一部分"快"发生在计时器之后

`worker-iocp-vs-cli-all-formats-20261002.json`，c=8，两者最终写入的字节数相同
（约 2400 MiB），差别在"什么时候算完"：

| 格式 | worker 提取 | worker 刷盘 | 合计 | 7z.exe 提取 | 7z.exe 刷盘 | 合计 |
| ---- | ----------- | ----------- | ---- | ----------- | ----------- | ---- |
| 7z non-solid | 1280.6 | 113.3 | 1425.9 | 550.3 | 318.3 | 890.9 |
| 7z solid | 875.3 | 170.6 | 1081.9 | 550.6 | 245.0 | 822.6 |
| 7z-split | 752.6 | 201.2 | 983.1 | 573.4 | 221.4 | 815.8 |
| bz2 | 4072.5 | 590.3 | 4689.1 | 4146.9 | 408.2 | 4575.0 |
| tar | 388.8 | 324.5 | 737.1 | 387.7 | 281.9 | 689.8 |
| tgz | 431.7 | 275.2 | 732.8 | 430.2 | 281.9 | 732.2 |

读法：

- 7z.exe 的"550 ms 写完 2400 MiB"是 **4.4 GiB/s**，超过设备持续速率 3.1 GiB/s，
  所以那 550 ms 里必然有相当一部分脏页还没落盘——随后 245–318 ms 的刷盘就是它。
  加上刷盘后，7z non-solid 890.9 ms、7z solid 822.6 ms。
- worker 的完成语义是"IO 已完成"，所以它的提取时间里已经包含设备时延；两者相加
  后差距远小于"1.5x"，bz2 / tgz / tar 基本持平。
- 因此修复目标不是"追平 550 ms"，而是"让 worker 的提取时间逼近
  `max(解码时间, 设备时间)`"，即 `max(532, ~770) ≈ 770 ms`。当前 747–790 ms
  已在这个量级，剩余可争的是 7z solid 的 875–1281 ms 那一段。

### 3.8 被否掉的假设：把驻留额度改成"提交时归还"

假设：容量既然只在完成时归还，就把 `job->inflight_bytes` / `file->inflight_bytes`
改成在 `WriteFile` 提交成功那一刻释放（缓冲仍被 IO 持有到完成），让在飞字节窗口
只限制"已解码未提交"的部分，从而解除设备时延对解码的反向门控。

实现要点：新增 `release_submitted_residency_locked()`，在 `enqueue_staging_locked()`
成功入队后调用；`release_buffer()` 不再动 `inflight_bytes`；`outstanding_data` /
`pending_jobs` 保持不变（它们是"已提交未归还"的缓冲数，close 顺序依赖它们——
第一版把它们一起挪到提交点，直接导致 `result failed: archive item could not be
written safely`，因为 close 在数据写完之前就被入队了）。

对照构建：`build-probe-before`（仅本改动之前）与 `build-probe`（含本改动），
两边都带同一套探针，c=8、`writers8`、3 轮：

| 配置 | 墙钟 | 核数 | 吞吐 | 单次写 | `inflight_peak` | `file_full` | `buffers_empty` |
| ---- | ---- | ---- | ---- | ------ | --------------- | ----------- | --------------- |
| before，池 64 | 768.4 | 6.52 | 3124 | 10.66 ms | 39 | 0 | 1524 |
| after，池 64 | 819.2 | 5.57 | 2930 | 10.36 ms | 25 | 0 | 1526 |
| before，池 256 | 920.2 | 5.33 | 2608 | 58.86 ms | **77** | 0 | 1064 |
| after，池 256 | 852.2 | 5.89 | 2816 | 43.31 ms | **97** | 0 | 953 |

结论：**该假设被否掉**。

- 它确实解除了耦合：`file_full` 归零，池 256 时在飞深度被推到 **77–97**。
- 但吞吐没有任何提升，反而在深队列下更差（单次写时延从 ~10 ms 涨到 43–59 ms）。
  在飞 25 / 39 / 77 / 97 四档对应的吞吐是 2930 / 3124 / 2608 / 2816 MiB/s——
  **与深度无关**，说明设备在 32 左右就已经饱和，加深只增加排队时延。
- 因此真正绑定的是**窗口太小**（8 MiB 只有饱和深度 32 MiB 的四分之一），
  不是"归还时机"。把窗口调够就等价达到上限，不需要动语义。

### 3.9 配对验证：窗口不是那个绑定约束（结论被推翻）

第 3.5 节的 `file_full` 归零曾被解读为"8 MiB 窗口在饿死提交"。配对验证否掉了这个
解读。

第一次扫描（`worker_window_sweep.py`，每个窗口值各编一个二进制、交替顺序各 4 轮）
确实显示 8 MiB 落后：中位数 815.9 ms（8 MiB）/ 742.0 ms（16 MiB）/ 768.4 ms（32 MiB），
`file_full` 1580 / 92 / 23。但那 4 轮里 8 MiB 的自己人极差就有 105 ms，
所以这个差异不足以立论。

于是做**同二进制、只改环境变量**的严格配对（`worker_paired_ab.py` 支持
`--before-file-inflight-mib` / `--after-file-inflight-mib`，两边各 4 轮交替）：

| 对比 | 并发 | 前 | 后 | 中位数 | 后胜 | 收益 |
| ---- | ---- | -- | -- | ------ | ---- | ---- |
| 8 → 16 MiB | 4 | 335.8 / 365.6 / 365.2 / 357.9 | 350.0 / 379.1 / 374.9 / 407.0 | 361.5 → 377.0 | **0/4** | **−4.28%** |
| 8 → 16 MiB | 8 | 787.8 / 799.6 / 787.0 / 786.8 | 836.4 / 748.9 / 757.2 / 813.3 | 787.4 → 785.2 | 2/4 | +0.27% |
| 16 → 64 MiB | 4 | 378.4 / 379.6 / 388.0 / 375.8 | 372.6 / 413.0 / 378.0 / 390.5 | 379.0 → 384.2 | 2/4 | −1.37% |
| 16 → 64 MiB | 8 | 854.7 / 862.5 / 757.5 / 777.3 | 779.1 / 829.1 / 855.4 / 750.5 | 816.0 → 804.1 | 3/4 | +1.46% |

结论：

- 窗口从 8 MiB 加到 16 / 64 MiB，墙钟差异都在 ±1.5% 内且符号不一致；
  c=4 时 8 MiB 还**四轮全胜**。窗口大小不是绑定约束。
- 第 3.5 节"深度 = 窗口"这个观察本身没错（改小窗口深度确实跟着降到 8），但
  **深度只有 8 的每文件在飞，并不限制总吞吐**：每作业有 2 个活跃文件、并发 8 个
  作业，聚合约 128 MiB，本来就超过设备饱和所需的约 88 MiB。`file_full` 是**每文件**
  上限的计数，把它当吞吐瓶颈是错的。
- 到这里，第 3 节里所有"窗口/线程/额度/池"的旋钮都被配对测量否掉了。剩下的差距
  只有两个真实来源：**设备持续写入速率（约 3.1–3.3 GiB/s）** 与 **7z.exe 把落盘推到
  计时器之后**（第 3.7 节）。worker 的 785–790 ms 已经贴着 `max(解码 532, 设备 770)`
  这个下界。

### 3.10 公平计时：把落盘算进来之后还剩多少差距

第 3.7 节指出了计时口径问题。这里把它修成可比较的度量，新增
`benchmarks/scenarios/worker_fair_timing.py`：每次运行测三段——

- `wall_ms`：进程/worker 返回（与 `worker-concurrency-300m` 一致）
- `flush_ms`：返回后立刻用 Rust `sync_all` 强制刷产出树（复用已有 `--sync-tree`）
- `wall_ms + flush_ms`：两台引擎都真正落盘的时刻，本文只认这个数

**顺手修掉的两个 benchmark bug**（都会让结果失真）：

1. `run_cli` 与 `worker_writer_ablation` 在 `-aoa` 之前没有清空输出目录。
   `-aoa` 只在单次调用内覆盖，跨 run 复用同一目录会让重名条目变成
   `large-00(1).bin`，校验看到的字节数直接翻倍。
2. `worker_writer_ablation.py` 的结果记录在 `--format` 之间互相覆盖，
   只有最后一个格式留在 JSON 里。

**A. 解码侧对照**（worker 内存接收器 = 完全不写盘；`7z.exe` 写到临时目录后删除）。
c=8，8 作业 × 300 MiB = 2400 MiB 解码输出：

| 格式 | worker | 核数 | 7z.exe | 核数 | worker/7z |
| ---- | ------ | ---- | ------ | ---- | --------- |
| 7z | 507.5 | 6.09 | 531.5 | 6.37 | **0.95** |
| xz | 527.2 | 9.21 | 717.1 | 7.21 | **0.74** |
| tgz | 168.6 | 6.48 | 429.3 | 5.32 | **0.39** |
| tar | 94.6 | 5.93 | 412.0 | 4.48 | **0.23** |
| zip | 152.9 | 7.56 | 437.1 | 5.58 | **0.35** |
| 7z-split | 512.4 | 8.70 | 627.2 | 8.42 | **0.82** |

**解码侧 worker 在所有格式上都更快**（7z 快 5%，xz 快 26%，tar 快 4.4 倍）。
第 3.2 节那个"关掉写入后 worker 更快"的观察在这里用公平的对照被确认：
早先那版 `--dry` 对 `7z t` 是不公平的（worker 不算 CRC、`7z t` 算）。

**B. 公平总时间**（提取 + 强制刷盘），c=8，整批写 2400 MiB：

| 格式 | worker 解码 | worker 提取 | worker 刷盘 | **worker 合计** | 7z 提取 | 7z 刷盘 | **7z 合计** | 提取比 | **合计比** |
| ---- | ----------- | ----------- | ----------- | --------------- | ------- | ------- | ----------- | ------ | ---------- |
| 7z | 507.5 | 795.9 | 143.0 | 949.7 | 557.2 | 264.8 | 821.1 | 1.43 | **1.16** |
| xz | 527.2 | 828.6 | 177.7 | 1006.2 | 624.9 | 162.3 | 799.2 | 1.33 | **1.26** |
| tgz | 168.6 | 390.2 | 313.3 | 703.5 | 434.6 | 291.0 | 721.6 | 0.90 | **0.97** |
| tar | 94.6 | 432.7 | 280.5 | 705.4 | 406.1 | 311.4 | 692.9 | 1.07 | **1.02** |
| zip | 152.9 | 593.2 | 600.0 | 1385.1 | 665.7 | 727.9 | 1472.5 | 0.89 | **0.94** |
| 7z-split | 512.4 | 1062.1 | 537.0 | 1594.7 | 893.6 | 659.4 | 1498.3 | 1.19 | **1.06** |

修正计时后的结论：

- **tar / tgz / zip 已经反超**（合计比 1.02 / 0.97 / 0.94）。
- **只剩 7z（1.16）与 xz（1.26）还有真实劣势**，比"原口径"的 1.43 / 1.33 小。
- 这个劣势**不是解码造成的**（A 表明解码 worker 更快），也不是"等容量"造成的
  （第 3.8 / 3.9 节已否掉）。看数字本身：
  worker 的提取时间 795.9 ms 里已经把整批 **2400 MiB 的落盘**做完了
  （2.94 GiB/s 的设备持续速率），而 7z 的 557 ms 只推了约 1.2 GiB，剩下约 1.2 GiB
  留给刷盘。也就是说，worker 的提取时间已经包含"设备把 2400 MiB 全部写下"这件事，
  7z 的提取时间没有。
- 用 `max(解码, 设备写入)` 检验重叠质量：7z 是 `max(507, 2400MiB/3.0GiB/s ≈ 767) ≈ 767`，
  实测 796 ms，只多 29 ms（3.8%）——**解码与落盘几乎完全重叠**，没有浪费。
  差距落在刷盘段（worker 143 ms 对 7z 265 ms 写残余脏页），属于内核回写时序。

### 3.2 关掉写入后 worker 反而更快——差距 100% 来自输出路径

> 注意：本节用的是早先的 `--dry` 对 `7z t`，那个对照**不公平**（worker 不算 CRC，
> `7z t` 算）。公平版本见第 3.10 节 A 表，结论方向相同、幅度更大。

`--dry`（worker `dry_run` 对 `7z t`），2 轮中位数：

| 格式 | 并发 | worker 墙钟 | worker 核数 | 7z.exe 墙钟 | 7z.exe 核数 | 比值 |
| ---- | ---- | ----------- | ----------- | ----------- | ----------- | ---- |
| 7z non-solid | 1 | 140.0 | 1.34 | 177.1 | 1.06 | 0.79 |
| 7z non-solid | 8 | 502.1 | 6.32 | 294.6 | 7.98 | 1.70 |
| 7z solid | 1 | 109.4 | 1.71 | 135.9 | 1.62 | 0.81 |
| 7z solid | 8 | 441.2 | 7.61 | 294.4 | 14.09 | 1.50 |
| xz | 1 | 104.9 | 2.38 | 122.4 | 1.87 | 0.86 |
| xz | 8 | 475.5 | 8.94 | 269.1 | 15.39 | 1.77 |
| tar | 1 | 45.3 | 1.04 | 51.6 | 0.91 | 0.88 |
| tar | 8 | 93.1 | 5.54 | 96.2 | 6.10 | 0.97 |

c=1 时 worker 快 12–21%；c=8 时慢 50–77%，而且**用的核更少**
（7.6 vs 14.1、8.9 vs 15.4）。核更少、时间更长，说明不是算力不够，是被挡住了。

对比同一格式打开写入的结果（3.1 节 833 ms vs 3.2 节 502 ms）：输出路径单独贡献
约 330 ms，而写入路径的**纯 CPU 开销**远小于此，差额是等待。

### 3.3 排除了所有配置旋钮

`few_large:7z:non-solid`，真实写入，第 2 轮中位数：

| 变体 | c=1 | c=4 | c=8 |
| ---- | --- | --- | --- |
| default | 209 | 393 | 802 |
| writers1 | 207 | 577 | 1021 |
| writers8 | 209 | 386 | 771 |
| writers16 / writers32 | 209 / 212 | 372 / 377 | 780 / 720 |
| buffers256 | 213 | 381 | 786 |
| spacegate_off | 209 | 386 | 764 |
| cap8 / cap16 / cap64 | 211 / 209 / 212 | 382 / 389 / 392 | 737 / 793 / 755 |
| prefetch_off | 204 | 354 | 705 |
| 7z.exe 参考 | 258 | 334 | 567 |

- 把每卷 writer 线程从 8 提到 16/32 没有改善，说明 IOCP 消费线程数不是限流点。
- 把 `SUNPACK_ASYNC_WRITER_BUFFERS` 从 64 提到 256 没有改善。
- 把 `thread_capacity` 提到 64 没有改善，说明全局 CPU 额度不是限流点。
- 关掉卷空间 gate、改 prefetch 都只有个位数百分比。

唯一显著动过瓶颈的是**放窗口**：把 `kDefaultFileInFlightBytes` 从 8 MiB 临时改成
32 MiB 后，`file_full` 从 1641 次降到 12 次，`inflight_peak` 从 8 升到 32，
c=8 从 833 ms 降到 734 ms。这确证了根因 1 与根因 2 是同一个机制的两端。

### 3.4 每作业并行度上限：额度给了也用不上

对**单个** 7z 作业做解码（`--dry`）扫描：

| 参数 | 额度 | 墙钟 | 核数 | 解码器峰值额外额度 |
| ---- | ---- | ---- | ---- | ------------------ |
| default | 32 | 145.1 | 1.40 | 1 |
| cap8 | 8 | 138.4 | 1.35 | 0 |
| cap16 | 16 | 139.1 | 1.12 | 1 |
| cap64 | 64 | 141.0 | 1.66 | 1 |

给到 64 个核的额度，单作业仍然只有约 1.2–1.7 核，解码器峰值额外额度始终是 1。
即：这里限流的不是 `NativeCpuBudget`，而是 `Lzma2DecMt` 对这批归档的切块结果——
非 solid 每个 folder 是一个 150 MiB 的解码单元，MT 侧拿不到更多可并行块。

同样现象在并发维度复现：默认额度下 `peak_decoder_extra_credits` 在 c=1/4/8
全是 1，且 c 从 8 增到 16 时 worker 的核数不升反降（5.2–5.8），而 `7z.exe` 从
13 核升到 20.6 核。**额度确实是够的**（c=16 默认 32 额度：16 个基础额度占用后
仍余 16），只是解码路径没有把它变成并行。

注意这一项**不能解释** c=8 那次差距：c=8 时 worker 用了 6.3–8.9 核、`7z.exe`
用了 8.0–15.4 核，worker 的**每核产出反而更高**；它是高并发下（c≥16）的天花板，
不是 c=8 落后的原因。c=8 落后的原因是第 3.1 / 3.5 / 3.6 节的写入深度。

## 4. 因果链

1. 解码线程在 `AsyncFileOutStream::Write` 里进入按卷共享的 `AsyncFileWriter`
   （`VolumeWriterRegistry` 用 `output_volume_key` 索引，同一输出卷的所有作业共用
   一个实例、一个缓冲区池、一个 IOCP 完成端口）。
2. 写入受三重窗口约束：每文件 8 MiB（`kDefaultFileInFlightBytes`）、每作业
   32 MiB（`kDefaultJobInFlightBytes`，`job_buffer_budget` 未设时）、全卷 64 × 1 MiB
   共享缓冲区池。
3. 这些窗口只在**完成路径** `release_buffer()` 里归还。提交成功不等于归还容量，
   所以"未完成 IO 数"被窗口大小锁死，实测 `inflight_peak` 恒等于窗口深度
   （8 MiB 窗口 → 8，32 MiB 窗口 → 32），与 IOCP 线程数无关。
4. 设备需要约 30 MiB 在飞才到 3.1 GiB/s 的持续速率；窗口只有 8 MiB 时，
   生产侧被设备时延拖住，解码线程停在 `producer_cv_.wait`（`capacity_wait`），
   LZMA2 的 MT 解码流水线随之停摆，CPU 空转。
5. `7z.exe` 把同步写塞进页缓存即返回，从不因写入时延门控解码；c 个进程各自独立，
   于是它把相当一部分落盘工作推到计时器之后（第 3.7 节），并发度越高差距越明显。

这同时解释了"为什么 7z / XZ / TXZ 差距最大"：三者都是**单一大 LZMA2 流**，
每个作业可用的解码并行度本来就最低，因此对"输出被卡住"最敏感；而 gz / zip /
tar 的解码本身核数低、`memory` 与 `real` 的差值是绝对值而非倍数，掩盖了同一机制。

## 5. 若要修，按性价比排序

**先说结论：队列深度类改动全部被配对测量否掉**——提交时归还（3.8）、加深每卷
writer 线程（3.5）、放大缓冲池（3.5）、放大每文件窗口（3.9）都没有可复现收益。
公平计时（3.10）之后只剩 7z / xz 有真实劣势，且解码侧 worker 更快。

按性价比排序：

1. **先修 benchmark 口径，再看差距**（已完成，见 3.10）：
   一律用 `worker_fair_timing.py` 的"提取 + 强制刷盘"口径，并保证每个 run 有干净
   输出目录。旧口径把 7z 的 245–318 ms 脏页刷盘算在了计时器之外，同时也把
   worker 已经落盘的字节算成了"还没完成"。
2. **同文件内改成有序流水**：`WriteFile` 在同一文件对象上本身是顺序语义，
   可在 `FileState` 层维护"下一个待写偏移"，让同文件的多个缓冲按序排队提交。
   这是唯一还没被否掉的 IO 侧改动；它只可能改善 7z / xz 这类"单一大流"的作业。
3. **提高单作业解码并行度（真正的天花板）**：c=16 时 worker 只用 5.2–5.8 核，
   而 `7z.exe` 到 20.6 核；c=1 给满 32 额度也只有 1.2 核、解码器峰值额外额度恒为 1。
   需要单独排查 `MtDec` 的切块/线程启动时机。
4. 次要项：`producer_cv_.notify_all()` 每次归还容量唤醒全部生产者（16 个），
   改成按需唤醒；完成路径每 1 MiB 要多次取同一把 `mutex_`，可合并成一次。
   这两项只减少空转，不改变吞吐上限。

要防止的四类"假修复"：加深每卷 writer 线程数、改成提交时归还、放大窗口/缓冲池、
以及靠降低并发或加等待来掩盖（项目明确禁止）。

**方法论提醒**：本节每一个"有效"结论都曾在单轮或单组对比里出现过，只有交替顺序的
配对测量才把它们区分开。单轮极差可达 50–105 ms（10% 以上），任何小于这个量级的
改动都必须配对验证。
