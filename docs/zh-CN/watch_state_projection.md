# Watch 的 GUI 状态日志

`state.snapshot` 和现有 WAL 是任务恢复依据；`.sunpack_watch/events.jsonl` 是 GUI 的唯一任务数据源。JSONL 不是第二套任务数据库。启动时不信任上次运行的结果，Scheduler 完成已有的恢复、缺失记录清理与阻塞重检后，从 Rust 常驻状态重建投影。旧成功历史可以被丢弃。

同一进程内，指向同一 Windows 路径的 `WatchLogStore` 共享一个 Rust 协调器和写入线程。Python 只传递事件；序列化、任务投影、字节预算、文件 IO 和压缩均由 Rust 执行。阻塞记录的发布和删除复用 `NativeWatchState.apply`，分卷关系保存在已有失败记录的 `failure_payload.ui_group` 中，恢复时不重新探测压缩包。

正常更新追加 JSONL。有效任务不受固定文件大小限制；最近结果和诊断各有 256 KiB 的默认预算。预计追加后的无效字节达到 `max(256 KiB, 有效投影字节数 / 2)` 时，写线程改为发布快照。快照保留每个有效任务的成员关系和最新状态；已完成历史按预算淘汰。待写队列默认上限为 1 MiB，超限后合并为最新投影，避免 IO 堵塞导致内存无限增长。

压缩写入同目录临时文件，完成 flush 和文件同步后使用 Windows 原子替换。普通追加不逐条同步。失败时保留内存投影并撤销可信性；下一次实际提交触发完整重写，不使用空闲轮询。最后一个所有者关闭时排空写线程，文件和内存对象随所有者释放。

GUI 协议包含：

- `state_begin`：协议版本、运行代际、进程 PID 与创建时间。
- 普通任务事件：成员关系、处理中、等待密码、缺卷、完成、失败、移除等。
- `state_ready`：本代际已完成恢复。
- `state_commit`：这一批发布的修订号。

代际对应的 Windows 命名事件和共享修订号只存在于内存，不保存任务数据。任务状态提交时立即撤销可信性；写线程追上最新状态修订后恢复可信性。纯诊断追加不改变状态修订，也不使任务卡片反复切换可信性。GUI 同时校验进程创建时间、进程存活、恢复完成标记、发布健康状态和实际读到的修订号。进程退出、写入失败、半行、解析失败或读到旧状态文件时，卡片显示“状态未验证”，并撤销输出成功导航。旧版无代际日志也视为未验证。GUI 使用进程和内核事件等待通知，不做保活轮询。

断电后，内核发布身份消失，因此磁盘上的旧 `state_ready` 不能让旧状态继续可信。下一次 Watch 启动仍由 WAL 恢复并重新发布，覆盖 WAL 提交与 GUI 日志更新之间的窗口。该机制保证无法验证时不宣称旧状态准确，不承诺在后台尚未恢复时凭 JSONL 推断真实任务结果。

`runtime-*.state.events.jsonl` 和 `toast_host_events.jsonl` 是异步、有界的诊断日志。启动器失败写入独立的 `bootstrap.events.jsonl`，避免另一个进程覆盖活动 Watch 所有者的投影。普通写入不等待磁盘；显式 flush 和生命周期结束时的 drain 是等待边界。
