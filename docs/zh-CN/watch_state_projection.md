# Watch 的任务投影日志

`state.snapshot` 和现有 WAL 决定任务恢复；`.sunpack_watch/events.jsonl` 供 GUI 顺序读取已经发布的任务状态。GUI 不读取 WAL，也不启动或调用 Python/Rust 主程序。后台不依赖 GUI 可执行文件。

## 展示边界

GUI 只展示处理中、等待密码、缺卷和终态。恢复尚未完成、旧运行已经退出或日志发布发生故障时，不展示该代际的任务，不生成“状态未验证”卡片、筛选项或提示。`pending_work` 只用于后台恢复，不意味着已经调度；清除最后一个阻塞记录会移除等待卡片，真实处理开始后再发布处理中。

普通追加允许很短的异步发布延迟：界面显示最后完整读到的 JSONL 记录，不承诺与后台内存每一瞬间严格一致。半行留到文件下一次实际变更再读，不撤销其他已发布状态。真实数据损坏仍保留现有错误计数和必要提示；短暂的读共享冲突不会变成任务状态。

## 恢复与发布

启动复用 Scheduler 已有恢复、记录清理和阻塞重检流程。完成后从 Rust 常驻的有效阻塞记录重建日志，旧处理中及成功历史可以丢弃，不把 WAL pending 记录转换为排队卡片。

分卷关系来自 Pipeline 已确认的分组，随 `WatchStateStore.mark(source_group=...)` 写入现有失败记录的 `failure_payload.source_group`。WAL 不从日志投影反查分组；恢复兼容读取旧的 `ui_group` 元数据，并只核对已记录成员是否存在，不重新分析压缩包。请求内的分组引用在完成、异常及取消时释放。

协议只需要 `state_begin`（代际、进程身份）、普通任务事件和 `state_ready`（恢复完成）。没有 `state_commit`、共享内存修订号或 dirty/published 双事件。

GUI 对每个新代际验证一次 PID 和进程创建时间，并通过一个阻塞等待监听进程退出或发布故障。后台仅保留一个故障事件，普通更新不触碰它；真正写盘失败、WAL 故障或所有者关闭时才使其失效。故障后下一次实际写入完整重建快照，使用新的代际和故障事件，旧文件始终保持失效。这保留了磁盘满/写入失败时隐藏陈旧活动状态的能力，没有逐任务、逐更新的跨进程同步。

压缩写入同目录临时文件，flush 并同步后原子替换；普通追加不逐条同步。复用资源生命周期屏障保护关闭临时文件到替换之间的窗口。写入错误可通过日志对象的 `error` 或显式 `flush` 观察，不启动空闲重试。

## 生命周期和预算

同一 Windows 路径共享一个 Rust 协调器和写线程。Python 只传递已经存在的元数据；Rust 转换一次后维护有界增量与最新投影。WAL 的状态图锁在日志序列化和投影操作前释放。

有效任务及其成员不设无意义的大小上限。最近结果和诊断各有 256 KiB 默认预算，待写增量上限 1 MiB；超出队列预算时折叠为最新投影。预计无效字节达到 `max(256 KiB, 有效投影字节数 / 2)` 时压缩。因此总内存与空间是 `O(有效任务及成员 + 固定历史/队列预算)`，不能把“1 MiB 队列”当作总内存上限。

物理成员退休只更新该成员；显式 `scope: task` 才退休整个逻辑任务。清除阻塞不制造排队状态；请求释放时清理仍属于它、却没有结果的处理投影，已经转交其他请求的任务不受影响。单个文件删除直接查成员索引，只有目录递归删除需要遍历任务。任务清空后释放散列表容量。

诊断正文在 Python → Rust 转换时限制为 4 KiB 文本预算、64 项和 8 层，并标记截断，避免复制/编码完整的巨大错误字符串。任务路径、输出路径、分卷关系不截断。纯诊断模式从不创建活动任务表，跨重启读取有限尾部并按实际磁盘长度计数；首次提交仍压缩发布。`runtime-*.state.events.jsonl`、`toast_host_events.jsonl` 都异步写盘；显式 flush 和关闭 drain 是等待边界，没有新增轮询。

可运行 `python -m benchmarks scheduling event-log --tasks 5000 --rounds 5 --cold-starts 40` 测量调用线程提交、最终排空、分组压缩、内存和连续短启动。性能测量不作为正确性测试。

## 本次验证

2026-10-24 在同一台 Windows 机器上，对审计提交和修复版各运行 5 轮、每轮删除 5000 个活动任务，得到以下中位数。这里测量的是事件元数据路径，不代表解压吞吐量；排空仍受磁盘调度影响，修复版也出现过约 79 ms 的单轮耗时。

| 测量 | 审计提交 | 修复版 |
| --- | ---: | ---: |
| 调用线程提交全部删除事件 | 84.84 ms | 6.29 ms |
| 提交至最终排空总耗时 | 85.95 ms | 8.90 ms |
| 40 次诊断日志短启动的最大文件长度 | 6291 字节 | 6291 字节 |

跨重启无界增长的审计推断未被复现：原版首条提交也会强制重写。修复仍按实际文件长度初始化计数，并保留连续短启动回归覆盖。

修复版另运行了 160 批持续生命周期负载，每批创建并释放 1000 个三成员任务。每批释放后日志均为 298 字节，单个写线程运行期间的总线程数/句柄数始终为 5/164，关闭后为 4/162。私有内存从约 13.4 MiB 上升至约 20.9 MiB，最后 20 批保持该水平；此测量用于观察资源趋势，不能证明任意时长下没有泄漏。

验证期间，修复前后的基准都曾偶发 Windows 错误 5（拒绝访问），尚未定位触发来源；最后这轮 160 批及 40 次短启动未复现。写入错误现包含打开/替换阶段和路径，基准如实保留故障，不增加等待或静默重试。共享冲突注入测试覆盖了故障时隐藏旧状态，以及下一次真实提交后的完整重建。
