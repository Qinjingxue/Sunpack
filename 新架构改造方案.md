我认为这个方案整体上是对的，而且比现在的 `Filesystem → Relations → Detection(还夹着 Embedded) → Nested policy → Extraction` 清楚得多。它本质上把现在一个“大 Detection 管道”拆成了几个单一职责的阶段。

我会把最终结构定义成：

```text
Filesystem discovery
    │
    ├── RAR / 7z / ZIP ─────→ Relations
    │                            │
    │                            ├── confirmed
    │                            ├── blocked / incomplete
    │                            └── residual
    │
    ├── TAR / gzip / bz2
    │   xz / zstd ... ───────→ Detection
    │                            │
    │                            ├── confirmed
    │                            └── residual
    │
    └── unknown ─────────────────┐
                                 │
Relations residual ──────────────┤
Detection residual ──────────────┤
                                 ▼
                         Embedded discovery
                                 │
                                 ▼
        all confirmed logical archive inputs
                                 │
                    recursive ? authorization
                                 │
                                 ▼
                       Input planning/password
                                 │
                                 ▼
                            Extraction
```

这里最大的优点，是**每一层都只回答一个问题**。

| 层                       | 只负责回答                                    |
| ----------------------- | ---------------------------------------- |
| Filesystem              | “这个物理文件大概该走哪条路？”                         |
| Relations               | “这些物理文件共同构成哪个 RAR/7z/ZIP logical input？” |
| Detection               | “这个单文件是不是 TAR/压缩流等独立 archive？”           |
| Embedded                | “前面没确认的文件里是否藏着 archive？”                 |
| Recursive authorization | “这个已经确认的 archive 在递归场景下允许不允许执行？”         |
| Extraction              | “实际能不能成功解出来？”                            |

这个边界比现在漂亮很多。

## 1. 第一轮放 Filesystem，我赞成，而且当前代码已经完成了大半

这里你说得很准确。

当前 native：

`native/sunpack_native/src/scan/directory.rs`

本来就是：

```rust
scan_directory_snapshot(...)
{
    ...
    populate_relation_anchors(&mut records);
}
```

而 `populate_relation_anchors()` 又直接：

```text
probe_volume_anchor_records_cheap()
```

每个文件读最多大约 512B。

而这个所谓 `relation_anchor` 实际上已经不只是 relation：

```text
RAR
7z
ZIP
gzip
bzip2
xz
zstd
tar
MZ/SFX seed
```

都能识别。

所以它实际上已经是：

> **Filesystem cheap format classifier**

只是名字和后面的数据流仍然把它当 Relation 辅助信息。

这次重构后我反而建议把语义改正。

比如当前：

```text
relation_anchor
```

长期可以改成：

```text
format_seed
```

或者：

```text
file_probe
```

因为它已经是一个通用的便宜文件分类结果。

Filesystem 输出不应该只是：

```text
DirectorySnapshot
```

而应该逻辑上包含：

```text
filtered physical files
raw physical files
cheap file classifications
```

然后直接根据 seed 分流。

例如：

```text
format = rar/7z/zip
    → relation lane

format = tar/gzip/bzip2/xz/zstd
    → detection lane

format = ""
    → unresolved lane
```

这样 Detection 连“应该尝试哪个格式”都不需要再猜。

### 这里必须保留 raw snapshot

这个非常重要。

当前 Relations 能正确处理一些被 size filter 排掉的分卷成员，就是因为：

```text
raw_snapshot
+
filtered_snapshot
```

都保留着。

以后即使 Filesystem 已经开始分流，也不能变成：

```text
Filesystem filter
→ 被过滤文件彻底消失
```

应该仍然是：

```text
raw physical view       ← Relations / recursive policy 可看
filtered eligible view  ← 正常候选入口
```

只是路由发生在 Filesystem。

# 2. RAR / 7z / ZIP 全部进入 Relations，我认为是这次最重要的改动

这三个格式放在一起非常合理，因为它们共同具备：

```text
physical file != logical archive
```

的可能性。

单卷：

```text
1 physical file
=
1 logical archive
```

只是 Relations 的最简单情况。

分卷：

```text
N physical files
=
1 logical archive
```

SFX：

```text
carrier
+
possibly N data files
=
1 logical archive
```

所以 Relations 不应该只负责：

> “找分卷”。

而应该正式成为：

> **Archive Input Resolver**

这三个格式的普通包也交给它。

### RAR

Filesystem cheap seed 已经有：

```text
RAR4/RAR5
header CRC
volume flag
first/member
volume number
header encryption
```

Relations 只需要决定：

```text
volume=false
→ standalone RAR input

volume=true
→ collect/validate volume family
```

普通和分卷走同一套逻辑。

### 7z

已经有：

```text
start header CRC
expected logical size
```

所以：

```text
physical_size >= logical_size
→ standalone

physical_size < logical_size
→ seek volume family
```

也是天然统一。

### ZIP

ZIP 稍微特殊，因为普通 ZIP 的强信息主要在尾部。

所以：

```text
Filesystem：
local header / split marker cheap seed

Relations：
候选 ZIP 才读 tail
→ EOCD
→ disk state
→ standalone / split
```

即可。

而不是：

```text
Relations 检查 ZIP split
+
Detection 再检查 ZIP standalone
```

---

# 3. Detection 以后应该变得非常“小”

RAR、7z、ZIP 拿走以后，Detection 的职责一下就干净了。

基本剩：

```text
tar
gzip
bzip2
xz
zstd
```

这些有一个共同特点：

> 一个物理文件基本就是一个逻辑 stream/container，不需要 sibling reasoning。

所以 Detection 可以成为真正意义上的：

```text
Single-file format validator
```

Filesystem 已经给它 format hint：

```text
gzip candidate
```

它就只跑 gzip validator。

而不是现在：

```text
五套 rule
每套都检查一下自己是否可能
```

这还顺便把现在的：

```text
format_reject_mask
routing_formats
routing_extensions
precheck promotion
```

大量复杂性削掉。

尤其你后面如果继续采用我们刚才讨论的原则：

> worker 是 correctness authority

那么 Detection 还可以进一步瘦成：

```text
TAR:
first header checksum

gzip:
header sanity

bz2:
BZh + block size

XZ:
header + CRC

Zstd:
frame header sanity
```

不用完整验证 payload。

最终 Detection 会从现在比较复杂的 rule/fact framework，收敛成一层非常轻的 single-file confirmer。

---

# 4. Embedded 独立成层，我认为非常值得

这也是当前架构一个很明显的混杂点。

现在 Embedded 分散在：

```text
detection/deep_scan.py

detection/pipeline/processors/
    embedded_payload/embedded_archive.py

detection/pipeline/rules/precheck/
    embedded_payload_identity.py

coordinator/nested_extraction_policy.py
    plan_embedded_scan()
```

也就是说：

> 扫不扫描 embedded、怎么扫描、结果怎么 accept、recursive 时谁能扫描

横跨 Detection 和 Nested policy。

这确实应该整体抽出去。

我会形成：

```text
EmbeddedDiscoveryLayer
```

它自己拥有现有的所有复杂 gate：

```text
embedded_scan.enabled

executable carrier classification

runtime_bundle exclusion

known SFX handling

recursive deep-scan candidate ratio

full-stream embedded Rust scanner

embedded candidate ranking
```

Detection 不再知道：

```text
embedded_archive.analysis
file.embedded_archive_found
executable.carrier
```

这些东西。

### Embedded 输入一定要是“剩余物理文件”

这个设计尤其好。

例如目录有：

```text
a.rar
a.part2.rar
b.zip
c.tar
setup.exe
resource.dat
random.bin
```

前面已经确认：

```text
a.rar + a.part2.rar
→ Relations claimed

b.zip
→ Relations claimed

c.tar
→ Detection claimed
```

Embedded 实际只需要看：

```text
setup.exe
resource.dat
random.bin
```

这比现在让 embedded rule 作为 Detection pipeline 的一个 rule 高效得多。

---

# 但这里有一个非常重要的状态设计

不能简单写成：

```text
not confirmed
→ Embedded
```

因为“没确认”其实至少有三种不同情况：

```text
RESOLVED
UNRESOLVED
BLOCKED
```

例如：

```text
RAR part1 + part3
缺 part2
```

Relations 可能知道：

> 这是一个 RAR family，但现在 incomplete。

它不能进入 Embedded，否则：

```text
part1.rar
```

又会被当普通文件扫一遍 embedded。

所以应该：

```text
RESOLVED
→ 后续候选

BLOCKED
→ 到此为止，等缺卷/password/file change

RESIDUAL / NOT_APPLICABLE
→ 才进入下一层
```

这是整个新流水线最重要的 contract 之一。

---

# 还需要有 `claimed_paths`

Relations 一旦确认：

```text
archive.part1.rar
archive.part2.rar
archive.part3.rar
launcher.exe
```

它必须返回：

```text
claimed_paths = {
    part1,
    part2,
    part3,
    launcher
}
```

于是后面的 Detection / Embedded 都绝不能再碰这些物理文件。

ZIP split、RAR SFX、companion 都一样。

否则虽然拆了层，但仍然会重复扫描。

因此新的每一层最好不是简单：

```text
input → outputs
```

而是：

```text
StageResult {
    resolved_inputs,
    claimed_paths,
    blocked_paths,
    residual_paths
}
```

这个模型会非常稳。

# 5. Recursive authorization 抽成独立层也完全正确

其实当前后半段已经非常接近你的设计。

`engine.py` 当前就是：

```text
scan_targets()
↓
NestedExtractionPolicy.authorize_batch()
↓
plan
↓
extract
```

而且：

```python
round_index <= 1
```

直接跳过 authorization。

所以你第五点：

> 非递归路径直接跳过

当前逻辑本来就是如此。

真正不合理的是 `NestedExtractionPolicy` 现在同时拥有：

```text
plan_embedded_scan()
```

和：

```text
authorize_batch()
```

这是两个完全不同的问题。

前者：

> 是否值得花成本扫描 embedded？

后者：

> 已经确认是 archive 了，递归环境允许不允许解？

应该彻底拆掉。

重构后：

```text
EmbeddedDiscoveryLayer
    └── EmbeddedScanGate

RecursiveAuthorizationLayer
    └── authorize confirmed archives
```

那么 Recursive Authorization 就可以真正对：

```text
Relations result
Detection result
Embedded result
```

一视同仁。

这个设计非常漂亮。

# 我甚至建议 Authorization 不再吃 `ArchiveTask`

当前：

```python
authorize_batch(tasks)
```

其实 native policy 真正需要的只有：

```text
entry_path
member_paths
raw filesystem snapshot
```

它根本不需要完整 Extraction Task。

所以更合理的是：

```text
ResolvedArchiveInput[]
        ↓
RecursiveAuthorization
        ↓
authorized ResolvedArchiveInput[]
        ↓
ArchiveTask / InputPlanning
```

也就是：

> **先授权，再生成真正 extraction task。**

这样 policy 就彻底与 Detection / Extraction 解耦。

# 6. Extraction 前最好统一成一个 contract

这是我认为这次架构重构能否真正成功的核心。

Relations、Detection、Embedded 最后都不要返回各自特色的：

```text
FactBag
RuleDecision
EmbeddedScanResult
CandidateGroup
```

然后 Coordinator 再猜该怎么转。

最好最终统一输出：

```text
ResolvedArchiveInput
```

项目已经有 `ArchiveInputDescriptor`，实际上非常适合继续发展。

例如概念上：

```text
ResolvedArchiveInput {
    format
    entry_path
    member_paths
    ranges
    structure_offset

    carrier_path
    companion_paths
    cleanup_paths

    source:
        relation
        detection
        embedded

    evidence
}
```

于是三条路最终全部合流：

```text
Relations ──┐
Detection ──┼──→ ResolvedArchiveInput[]
Embedded  ──┘
```

接下来：

```text
RecursiveAuthorization
→ InputPlanning
→ PasswordResolver
→ Extraction
```

这样以后 `FactBag` 就只属于 Detection 内部，而不会继续作为整个系统的公共总线。

我认为这是个很大的架构收益。

# 性能上这套架构也非常合理

现在大目录大致是：

```text
Filesystem enumerate
↓
cheap Rust anchor
↓
Relations
↓
Detection 又请求 structure facts
↓
可能 Embedded
```

重构后：

```text
Filesystem:
每个文件唯一一次 cheap classification
              ↓
      ┌───────┼─────────┐
      ▼       ▼         ▼
 Relations Detection unresolved
                       ↓
                    Embedded
```

最关键的是：

> **一旦某层 claim 了一个文件，后面彻底不再扫描。**

因此工作量是逐层递减的。

假设 10 万个文件：

```text
Filesystem        100000
Relations           300
Detection            80
Embedded             20
Extraction            8
```

而不是现在多个层对相同 archive 重复解析。

这正是高性能扫描系统应该有的形状。

# 对 recursive output 还有一个额外性能机会

当前 worker manifest 本身已经保存：

```text
size
mtime
magic
```

`DetectionScanSession.prime_file_head_columns()` 也已经会利用这些数据，避免部分 reopen。

如果第一层 cheap classifier 正式进入 Filesystem，那么递归 extraction 的输出甚至可以做到：

```text
worker 写文件时已经知道前若干 bytes
        ↓
output inventory
        ↓
Filesystem classifier 直接消费
```

而不是：

```text
文件刚写完
↓
Filesystem 再 open
↓
再读 512B
```

这不是第一轮必须做，但新架构会很自然地允许这个优化。

# 我认为最终最合理的主链就是

```text
┌──────────────────────────────┐
│ 1. Filesystem Discovery      │
│ enumerate / filters          │
│ cheap native classification  │
└──────────────┬───────────────┘
               │
       route physical files
               │
     ┌─────────┴──────────┐
     ▼                    ▼
┌─────────────┐     ┌─────────────┐
│2 Relations  │     │3 Detection  │
│RAR/7z/ZIP   │     │single-file  │
│single+split │     │formats      │
└──────┬──────┘     └──────┬──────┘
       │                    │
       └───────┬────────────┘
               │ residual only
               ▼
┌──────────────────────────────┐
│ 4. Embedded Discovery        │
│ gates + full-stream scanner  │
└──────────────┬───────────────┘
               │
      ResolvedArchiveInput[]
               │
               ▼
┌──────────────────────────────┐
│ 5. Recursive Authorization   │
│ round 1: bypass              │
│ round >1: native policy      │
└──────────────┬───────────────┘
               │
               ▼
       Input planning/password
               │
               ▼
┌──────────────────────────────┐
│ 6. Extraction                │
│ integrated 7-Zip authority   │
└──────────────────────────────┘
```

我认为这套比当前架构有一个根本提升：**Discovery 与 Validation 不再混在一起。**

Filesystem 负责发现和路由；Relations/Detection/Embedded 是三种互斥的 archive discovery strategy；Recursive policy 只决定是否允许；7-Zip 只决定实际执行是否成功。

如果真要开始做，我会建议第一步不是直接删 Detection 代码，而是先建立 **统一的 `ResolvedArchiveInput + StageResult(claimed/blocked/residual)` contract**，然后逐层迁移。这个 contract 一旦定下来，后面的 RAR/7z/ZIP 搬迁、Embedded 抽层、Recursive policy 拆分都会顺很多。
